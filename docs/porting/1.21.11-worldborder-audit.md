Based on my complete trace of both refs and the runtime/worldgen architecture, here is the definitive report. One critical finding reframes the entire investigation: I could not find proof that `isGlobeOverworld()` returns *false* — every adversarial refutation holds, and the in-game symptoms are actually consistent with the border simply never being broadcast. The report below states the single most-probable root cause with the decisive evidence, but is honest that the final discriminator requires one log line that only Maintainer/the engineer can read from the actual run.

# Latitude 1.21.11 — WorldBorder Not Applied: Root-Cause + Fix Plan

**Ref under test:** `port/1.4.0-beta-1.21.11` @ `f3261ba5` (MC 1.21.11, Yarn, beta.7)
**Working reference:** `feat/1.3.1-cohesive-horizons-26.1.2` @ `691e54b4` (MC 26.1.2, Mojmap)
**Audience:** Maintainer (mod author) + the fixing engineer
**Status of investigation:** READ-ONLY. No files modified.

---

## 0. TL;DR

All three symptoms (vanilla ~60M border, HUD ~0°, no start-compass) are **one failure with one downstream fan-out**: the server-side **`WorldBorder` is never resized**, so its half-size stays ~30,000,000. The HUD computes degrees as `z / halfSize(border)` → ~0° everywhere; the zone/biome distribution is *independent* of the border (it derives radius straight from the settings key), which is why biomes still look correct.

The popular hypothesis from the audit — that 1.21.11's `noise.matchesSettings()` (vs 26.1.2's `noise.stable()`) makes `GlobeMod.isGlobeOverworld()` return false — is **REFUTED** (the worldgen path calls the identical `matchesSettings()` on the same generator instance and demonstrably works). The persistence hypothesis (`goh.generatorOptions()` losing the preset) is **also REFUTED** (in 1.21.11 `GeneratorOptions` never carries dimensions; the dimensions flow through the registry manager, which the launcher populates correctly).

**The single mechanism that survives all evidence:** the `WorldBorder` set in `applyWorldBorder` (registered on `ServerLifecycleEvents.SERVER_STARTED`) **never reaches the client** on a freshly-created, bespoke-launched integrated world — either because the handler does not run / runs against the wrong server instance under the bespoke `client.startIntegratedServer(...)` launch path, or because the border resize is applied to the server border but not broadcast to the just-joined client. The decisive next step is reading two specific log lines from the actual run (Section 4) — they pinpoint which of the two it is in seconds.

## 1. The symptom chain (why three bugs are really one)

The HUD degree readout is computed entirely from the **client's mirror of the WorldBorder half-size**:

- `src/main/java/com/example/globe/client/CompassHud.java:420,426`
  `LatitudeMath.formatLatitudeDeg(client.player.getZ(), client.world.getWorldBorder())`
- `src/main/java/com/example/globe/util/LatitudeMath.java:51-60`
  `degreesFromZ = (z / halfSize(border)) * 90`, `halfSize = border.getSize() * 0.5`

With the border at vanilla `59999968`, `halfSize ≈ 29,999,984`. Any survivable `z` gives `≈ 0°`. **This exactly matches the reported "1°S / 0° everywhere," and matches the observation that `|z| / 30,000,000 ≈ 0`.** So "HUD reads 0°" is not an independent bug — it is the direct, arithmetic consequence of the border never being resized.

The compass grant and the border resize share the same root: they are the two server-runtime actions gated behind `isGlobeOverworld(...)`:
- Compass: `GlobeMod.java` JOIN handler, `if (isGlobe && !server.isDedicated() && !StartCompass.hasReceived(...))` (lines ~154-164).
- Border: `GlobeMod.applyWorldBorder` early-returns on `!isGlobeOverworld(overworld)` then `border.setSize(diameter)` (lines 261, 274).

The **only** place in the entire codebase that resizes the border is `applyWorldBorder` (verified by grep: `setSize`/`setCenter` appear once, GlobeMod.java:273-274). There is no per-tick re-assert and no level-load border set. So if the border is vanilla in-game, `border.setSize(...)` did not execute (or its broadcast did not reach the client).

## 2. Why "biomes work but the border doesn't" is NOT contradictory

This is the crux that misled the audit toward `matchesSettings`. Worldgen and the runtime border are **decoupled by design**:

- Worldgen biome placement runs through `LatitudeBiomeSource.getBiome()` → `LatitudeBiomes.pick(..., borderRadiusBlocks, ...)`
  (`src/main/java/com/example/globe/world/LatitudeBiomeSource.java:61-66`).
- `borderRadiusBlocks` is computed **from the chunk-generator settings key directly**, never from the `WorldBorder`:
  `ChunkGeneratorPopulateBiomesMixin.globe$borderRadiusBlocks()` and `ChunkGeneratorBiomeSourceMixin.globe$borderRadiusBlocks()` map `globe:overworld*` → 3750/5000/7500/10000/15000/20000.
- In `LatitudeBiomes.pick` (`LatitudeBiomes.java:991-998, 1226-1233`): `effectiveRadius = (activeRadius > 0) ? ACTIVE_RADIUS_BLOCKS : borderRadiusBlocks`. So even if `ACTIVE_RADIUS_BLOCKS` is never set by `applyWorldBorder`, worldgen falls back to the settings-keyed radius and **still distributes biomes by latitude correctly**.

**Therefore: biomes being latitude-correct proves only that the worldgen mixin ran with `matchesSettings()==true`. It says nothing about whether the WorldBorder was resized.** The two paths read the same generator's `settings` field but consume entirely different radius sources.

The "big TROPICAL title" is likewise NOT evidence that the runtime gate passed: `ZoneTitleOverlay` (`client/ui/ZoneTitleOverlay.java`) just renders a title handed to it by the client spawn-pick flow (`GlobePending`/spawn-zone selection from the bespoke create screen), not a value derived from the runtime border.

## 3. Refuted hypotheses (with the decisive code facts)

### 3a. `matchesSettings()` vs `stable()` — REFUTED
`noise.stable(ResourceKey)` (Mojmap) and `noise.matchesSettings(RegistryKey)` (Yarn) are the **same vanilla method** under two mapping sets. Decompiled:
`_mcsrc_yarn/net/minecraft/world/gen/chunk/NoiseChunkGenerator.java:69,74,128-129`
```java
private final RegistryEntry<ChunkGeneratorSettings> settings;   // final, set in the sole ctor
public boolean matchesSettings(RegistryKey<ChunkGeneratorSettings> settings) {
    return this.settings.matchesKey(settings);                  // identity-compares interned keys
}
```
`RegistryKey.of(...)` interns keys (`RegistryKey.java` `INSTANCES.computeIfAbsent`), so `Reference.matchesKey` (`==`) is sound. The worldgen mixins (`ChunkGeneratorPopulateBiomesMixin.globe$isAnyGlobeSettings`, `ChunkGeneratorBiomeSourceMixin.globe$isAnyGlobeSettings`) call this exact method on the same generator and **succeed in-game** (biomes are placed). `GlobeMod.isGlobeOverworld()` reads the same instance via `world.getChunkManager().getChunkGenerator()` (and `ServerChunkManager.getChunkGenerator()` returns the single live generator — `_mcsrc_yarn/.../ServerChunkManager.java:445-446`). The same method, same object, same keys cannot return true for worldgen and false here.

### 3b. "Missing null-check on settings makes matchesSettings silently fail" — REFUTED
`this.settings` is `final`, assigned in the only constructor, and the generator is actively generating chunks by `SERVER_STARTED`. A null would throw NPE (not silently return false), and the reported symptom is silent non-application with no crash. The mixin's `accessor.globe$getSettings() == null` guard exists only because the mixin injects at constructor `@At("TAIL")` (a construction-window guard), not because the runtime gate needs it. 26.1.2's `isGlobeOverworld()` *also* has no guard and works.

### 3c. "Launcher persists vanilla settings via `goh.generatorOptions()`" — REFUTED
In MC 1.21.11, `GeneratorOptions` holds only `{ seed, generateStructures, bonusChest, legacyCustomOptions }` — **it does not carry dimensions or chunk-generator settings** (`_mcsrc_yarn/net/minecraft/world/gen/GeneratorOptions.java:22-25`). The persisted dimensions are written from the **live DIMENSION registry**:
`_mcsrc_yarn/net/minecraft/world/level/LevelProperties.java:228` →
`WorldGenSettings.encode(ops, this.generatorOptions, registryManager)` →
`_mcsrc_yarn/net/minecraft/world/level/WorldGenSettings.java:27-28` reads `registryManager.getOrThrow(RegistryKeys.DIMENSION)`.
`LatitudeWorldLauncher.beginExpedition` (1.21.11) builds `combinedDynamicRegistries .with(DIMENSIONS, dimensionsConfig.toDynamicRegistryManager())` from `goh.selectedDimensions()` and passes it to `startNewWorld(...)`. The server's overworld is then constructed from `registry.get(DimensionOptions.OVERWORLD)` (`MinecraftServer.createWorlds`, `_mcsrc:457-461`), which references `globe:overworld`. **Hence both the running world and the saved level.dat carry globe settings** — consistent with worldgen working and with `matchesSettings()` being true at runtime.

> Net effect of 3a–3c: there is **no evidence that `isGlobeOverworld()` returns false**, and three independent reasons it should return *true*. The remaining failure must be in *reaching/broadcasting* the border resize, not in detection.

## 4. THE root cause (single mechanism) + how to confirm it in one step

**Root cause (most probable):** On the 1.21.11 bespoke create-world path, the `WorldBorder` resize performed by `applyWorldBorder` is never reflected on the client of the freshly-joined player. Two concrete variants remain, and they are distinguished by log lines that already exist in the code:

1. **`SERVER_STARTED` did not run `applyWorldBorder` against the live overworld.** The bespoke launcher starts the integrated server through `client.createIntegratedServerLoader().startNewWorld(session, dataPackContents, combinedDynamicRegistries, levelProperties)` → `client.startIntegratedServer(...)` (`_mcsrc_yarn/.../IntegratedServerLoader.java:140-153`), rather than vanilla `createWorldOpenFlows().createLevelFromExistingSettings(...)` used in 26.1.2. If Fabric's `ServerLifecycleEvents.SERVER_STARTED` fires before `server.getOverworld()` is populated, or the handler's `isGlobeOverworld` evaluates a not-yet-wired generator, `applyWorldBorder` returns early.

2. **The border was resized server-side but not broadcast to the joining client.** `border.setSize(diameter)` notifies the server border listeners; the just-connected client receives border state at login. A timing gap (resize at `SERVER_STARTED`, client connection slightly later or the integrated client's level border not re-synced) leaves the client mirror at the vanilla default — exactly the 30M the HUD divides by.

**Decisive confirmation (read the log from the broken run):**
- `GlobeMod.applyWorldBorder` emits, on success:
  `"[Latitude] WorldBorder set: radius={} diameter={} center=0,0 polarStart={}"` and the two `"[Latitude] Radius Sync: ..."` lines.
- The JOIN handler emits: `"JOIN: player={}, isGlobeOverworld={}"`.

Interpretation:
- **No `WorldBorder set` line at all** → `applyWorldBorder` never passed its gate or never ran → variant (1). Check the JOIN line's `isGlobeOverworld=` value: if JOIN logged `true` but no border line exists, `SERVER_STARTED` either didn't fire or ran with a null/early overworld.
- **`WorldBorder set` line present (radius=7500/15000/...)** but client still shows 60M → variant (2): server resized, client never got it → a broadcast/resync gap.
- **JOIN logged `isGlobeOverworld=false`** → would reopen 3a–3c, but that contradicts working worldgen; if you somehow see this, capture the generator's actual settings id (it would mean the JOIN handler ran against a different `server` than the one generating chunks — e.g., a stale `MinecraftClient.getServer()` vs the integrated instance).

This one log read collapses the remaining ambiguity. I could not read it (no running instance); it is the only missing fact.

## 5. Secondary / contributing issues (real, but not the cause of the 60M border)

These should be fixed in the same pass; none alone explains the symptom cluster.

1. **`spawnAlreadyChosen` guard deleted in the JOIN handler.**
   26.1.2 `GlobeMod.java:158`: `boolean spawnAlreadyChosen = handler.player.entityTags().contains(SPAWN_CHOSEN_TAG);` and gates spawn application on it. 1.21.11 dropped this and instead gates on `worldState.isSpawnPickerDismissed()` + sends `OpenSpawnPickerPayload`. This can re-trigger spawn/picker logic on rejoin. It is entirely inside the `isGlobe` branch, so it cannot cause a false-isGlobe symptom — but it is a behavior regression worth restoring.

2. **`formatLatitudeDeg` argument order looks swapped at the HUD call sites.**
   `CompassHud.java:420,426` call `formatLatitudeDeg(client.player.getZ(), client.world.getWorldBorder())` while `LatitudeMath.formatLatitudeDeg(WorldBorder border, double z)` (line 133) expects `(border, z)`. The same apparent order exists in 26.1.2, so it presumably compiles (there may be an overload or the 26.1.2 compiled signature differs). **Verify this compiles and is not silently swapped** — if swapped it is masked today only because the border is 30M (degrees ≈ 0 either way), and would surface as wrong degrees once the border is fixed. Confirm there is exactly one `formatLatitudeDeg` overload and that the order is correct.

3. **Border-radius constant inconsistency between the two worldgen radius mappers and `borderRadiusForGlobeOverworld`.**
   `GlobeMod.borderRadiusForGlobeOverworld(globe:overworld) = 15000`, but `ChunkGeneratorPopulateBiomesMixin.globe$borderRadiusBlocks(globe:overworld)` falls through to `GlobeMod.BORDER_RADIUS = 7500` (it only special-cases xsmall/small/large/massive, not the bare `globe:overworld`). For the "Large (30,000×30,000)" preset (`globe:globe` → `globe:overworld`), worldgen would seed radius 7500 while the border would be 15000 → a `RADIUS MISMATCH` warning and a biome/border disagreement. Mirror the full 6-key mapping in both worldgen mixins, or have all three call one shared mapping helper. (This is a latent worldgen-vs-border-size mismatch, not the 60M bug.)

## 6. Fix plan (precise, dependency-ordered, for `port/1.4.0-beta-1.21.11`)

> Do **not** change `GlobeMod.isGlobeOverworld()` to add a null-check or revert to a different match call — that is a dead end (Section 3). The fix is in *border application/broadcast timing* and the launch path.

**Step 0 — Diagnose first (mandatory, 5 minutes).** Reproduce on a fresh bespoke-launched world and capture the server log. Grep for `WorldBorder set`, `Radius Sync`, and `JOIN: player=`. This selects between Step 1 and Step 2 below. Do not write code before this read.

**Step 1 — If `applyWorldBorder` never logged `WorldBorder set` (variant 1: handler didn't run/gate failed):**
- Add a defensive re-application that does not depend solely on `SERVER_STARTED` firing at the right moment, mirroring 26.1.2's intent. Concretely, in `GlobeMod.onInitialize()` also resize the border from the existing `ServerWorldEvents.LOAD` handler (`initLatitudeBiomesForWorld`) for `server.getOverworld()`: after `LatitudeBiomes.setRadius(radius)`, also call the border resize there (extract the `border.setSize`/`setCenter` block from `applyWorldBorder` into a shared `setGlobeBorder(ServerWorld, int radius)` and call it from both `LOAD` and `SERVER_STARTED`). `ServerWorldEvents.LOAD` fires per-world during `createWorlds`, before `prepareStartRegion`, with the overworld present — this guarantees the border is set even if `SERVER_STARTED` timing differs on the integrated path.
- Keep `applyWorldBorder` on `SERVER_STARTED` as the authoritative second pass (idempotent: setting the same diameter twice is harmless).
- Mojmap→Yarn note: `ServerLevelEvents.LOAD` (26.1.2) ≡ `ServerWorldEvents.LOAD` (1.21.11) — already wired identically.

**Step 2 — If `WorldBorder set` logged but the client still shows 60M (variant 2: broadcast/resync gap):**
- Re-broadcast border state to players on join. In the JOIN handler, when `isGlobe`, after `ServerPlayNetworking.send(... GlobeStatePayload(true))`, force a border resync to that player. In Yarn 1.21.11 the integrated client shares the server border instance, but the *client level's* border mirror may lag; the robust fix is to (a) ensure the border is resized at `LOAD` (Step 1) so it is correct before any client connects, and (b) send the player the current border via the world border's initialize packet (`WorldBorderInitializeS2CPacket`) on join, or nudge `border.setSize(border.getSize())` after the player connects to trigger a broadcast.
- Prefer Step 1's LOAD-time application as the primary fix; it makes the border correct before the client's initial border snapshot is taken, which fixes variant 2 for free.

**Step 3 — Restore the `spawnAlreadyChosen` guard (Section 5.1).** Re-add `boolean spawnAlreadyChosen = handler.player.getCommandTags().contains(SPAWN_CHOSEN_TAG);` (Yarn: `getCommandTags()` is the equivalent of Mojmap `entityTags()`) and gate the spawn-apply block on `!spawnAlreadyChosen`, matching 26.1.2 `GlobeMod.java:158,176-188`. This prevents duplicate spawn/picker fires on rejoin.

**Step 4 — Unify the radius mapping (Section 5.3).** Make `ChunkGeneratorPopulateBiomesMixin.globe$borderRadiusBlocks()` and `ChunkGeneratorBiomeSourceMixin.globe$borderRadiusBlocks()` map all six keys identically to `GlobeMod.borderRadiusForGlobeOverworld()` (add the `globe:overworld → 15000` and `globe:overworld_regular → 7500` cases consistently). Best: one shared static helper used by all three.

**Step 5 — Verify the `formatLatitudeDeg` arg order (Section 5.2).** Confirm `CompassHud.java:420,426` pass `(border, z)`. If the parameter order is genuinely `(getZ(), getWorldBorder())` against a `(WorldBorder, double)` signature and it still compiles, find and document the overload; otherwise correct the order. This only manifests once the border is fixed.
